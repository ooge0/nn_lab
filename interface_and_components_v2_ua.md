Цей документ описує інтерфейс поточної версії застосунку: веб-застосунок на FastAPI + Jinja2 + HTMX, що замінив початковий інтерфейс на Streamlit, описаний у першому документі "Interface and components". Структура та рівень деталізації збережені такими ж, як у тому документі, з оновленням до фактичного стану реалізації та двома новими розділами, яких не було в оригіналі: каскад оцінювання відповідей та сторінка експорту в базу даних. Кожне поле, формула та назва сторінки нижче взяті безпосередньо з поточного коду, а не перенесені з попереднього документа без перевірки. Кілька формул відрізняються від оригінального документа, оскільки відповідне обчислення було виправлено під час цього переписування; кожен такий випадок позначено окремо.

Застосунок поєднує:

* Генерацію тексту LLM (Ollama, лише локальні моделі, без платного API) для контрольованих експериментів із різними архітектурами моделей.
* Структурований, багаторівневий каскад оцінювання, який класифікує та оцінює кожну відповідь до обчислення будь-якої метрики.
* Психолінгвістичний і статистичний аналіз (NLTK, TextBlob, spaCy, sentence-transformers) емоційності, когнітивного навантаження та мовних патернів.
* Візуалізацію (FastAPI + Plotly + Jinja2/HTMX) з інтерактивними графіками, теплокартами та кластеризацією для інтерпретації результатів.
* Збереження у форматі JSONL за замовчуванням, з можливістю експорту за запитом у реальну базу даних SQLite.


## Інтерфейс та компоненти (v2)

### Навігація та структура інтерфейсу

Окремого етапу збірки frontend немає. FastAPI обслуговує API та кожну HTML-сторінку з одного процесу (`uvicorn api.app:app --reload`). Інтерфейс — це фіксована бічна панель зліва плюс область контенту, а не система вкладок на одній сторінці.

* **Бічна панель** — згрупована у три позначені розділи:
  * `[req]` — сторінки рівня одного запиту: Generation, Performance, Model Evaluation.
  * `[corpus]` — сторінки рівня корпусу, які дають змістовний результат лише за наявності кількох відповідей: Analytics, NLP Science, Clustering, Benchmark.
  * `[sys]` — системні сторінки: System Monitor, Export to DB, FAQ.
* **Віджет статусу сервісів** — невеликий індикатор у бічній панелі, перевіряється при завантаженні кожної сторінки, повідомляє, чи доступні Ollama, ресурси NLTK та модель spaCy. Замінює індикатори статусу модулів оригінальної бічної панелі Streamlit; на відміну від оригіналу, він не керує сервісами і не перезапускає їх, лише повідомляє про доступність.
* **Перемикач теми** — перемикає між темною (на основі VS Code Dark+) та світлою палітрою, значення зберігається на стороні клієнта.
* Перемикача режиму Debug/Lab немає. Розрізнення оригіналу між режимами експерименту "debug" та "laboratory" не має відповідника; кожна сторінка однакова для будь-якого використання.

### Generation (`/experiments`)

Основна сторінка налаштування та запуску експерименту. Прогрес передається в реальному часі через Server-Sent Events, без опитування чи перезапуску Streamlit.

* **Student models** — одна або кілька моделей для генерації (множинний вибір, обов'язково).
* **Archetypes** — один або кілька поведінкових архетипів, на які орієнтована генерація (множинний вибір, обов'язково).
* **Biases** — довільний текстовий опис(и) зміщення, що додається у промпт.
* **Prompt mode** — одна з трьох стратегій побудови системного промпту:
  * *Behavioral conditioning (Tuned)* — повний системний промпт з урахуванням архетипу.
  * *Blind mode (Hide label)* — генерація без явної назви архетипу в промпті, використовується для перевірки, чи модель усе одно демонструє цільовий стиль без прямої вказівки.
  * *Raw / No system prompt* — без жодного обумовлення, базовий варіант.
* **Judging mode** — один із двох, взаємовиключних:
  * *Teacher–student* — окрема модель-вчитель оцінює вихід кожного студента. Потребує вибору моделі-вчителя.
  * *Self-critic* — модель-студент оцінює власний вихід. Задокументований ризик підлабузництва (sycophancy) (див. "Каскад оцінювання" нижче); інтерфейс не приховує цей ризик, він прямо розкритий у цьому документі та в коментарях самого коду.
* **RAG (retrieval-augmented generation)** — необов'язково. Якщо увімкнено, режим пошуку (лише архетип / архетип + bias) та кількість фрагментів Top-K визначають, який контекст із бази знань додається у промпт.
* **Sweep** — необов'язкова динамічна варіація одного параметра генерації (Temperature, Top P, Frequency penalty або Presence penalty) у діапазоні, або фіксованим кроком (режим Delta), або явним мінімумом/максимумом (режим MIN-MAX). За один запуск можна варіювати лише один параметр; справжній перебір по сітці кількох параметрів не реалізовано — свідоме рішення: комбінаторна вартість визнана невиправданою для однієї машини без кластера, що міг би прийняти додатковий час виконання.
* **Параметри семплінгу** — Temperature, Top P, Frequency penalty, Presence penalty, Max tokens, Seed. Використовуються як статичні значення, якщо не перевизначені активним sweep.
* **Живий попередній перегляд налаштувань** — панель на HTMX, яка перераховує точну кількість задач (`students x archetypes x biases x sweep steps`) під час зміни форми, до старту запуску.
* **Жорстке обмеження кількості задач** — налаштована стеля (`max_total_tasks`, за замовчуванням 500) перевіряється на сервері до початку генерації; завеликий запит відхиляється явною помилкою, а не лише показується у попередньому перегляді.
* **Керування зупинкою** — кооперативна зупинка: запит на зупинку виконується між задачами, а не посеред виклику генерації. Відповідь, яка вже генерується в момент запиту зупинки, завжди завершується та зберігається.

### Каскад оцінювання

Відсутній як окремий розділ інтерфейсу в оригінальному документі; це основний механізм, що визначає, чи згенерована відповідь буде зафіксована як валідна. Виконується автоматично для кожної відповіді, у фіксованому детермінованому порядку — спочатку найдешевші та найнадійніші перевірки, генеративний суддя — лише коли попередні рівні не можуть вирішити випадок. Цей порядок — заявлений принцип дизайну: каскад є конвеєром на основі правил, а не LLM, що вирішує, яку перевірку запускати.

* **Layer 0 — детермінована класифікація.** Кожна сира відповідь класифікується як одна з `VALID`, `MALFORMED_JSON`, `TRUNCATED`, `EMPTY` або `SCHEMA_ERROR` до обчислення будь-якої метрики. Класифікація, відмінна від `VALID`, повністю пропускає обчислення метрик та виклик судді, і фіксується як невдала.
* **Layer 1 — виявлення "відлуння" (echo detection).** Відповідь, чия оцінка семантичної подібності до власного тексту bias/інструкції перевищує калібрований поріг, відхиляється як відлуння — модель повторює власну інструкцію замість генерації обумовленого тексту, а не справді малоспоріднена, нерелевантна відповідь. Напрямок порогу (відхиляти високу подібність, а не низьку) було інвертовано відносно початкового задуму після калібрування на реальних згенерованих даних, яке показало, що для цього конкретного поля правильна протилежна інтуїція.
* **Layer 2 — перевірка на фактичне протиріччя.** Виконується лише коли увімкнено RAG, оскільки потребує отриманого контексту для звірки відповіді. Використовує локальну модель NLI cross-encoder. Наразі фіксує передбачену мітку та оцінку протиріччя для кожної відповіді, але нічого не відхиляє; поріг відхилення ще не калібрований на реальних даних.
* **Layer 3 — структурований суддя.** Генеративне рішення "пройшло/не пройшло": модель-суддя отримує запит на структурований вихід, і відповідь парситься як справжній JSON, повертаючи вердикт, значення впевненості та текстове обґрунтування. Відповідь, яку не вдалося розпарсити, вирішується як вердикт false із впевненістю 0.0 — значення, відмінне від справжнього негативного вердикту, а не тихо невідрізниме від нього.

### Performance (`/runs`)

Зведення персистованих відповідей одного завершеного (або поточного) запуску, лише для читання.

* **Вибір запуску** — обирає, дані якого запуску підсумовувати.
* **Поля зведення** — загальна кількість записів, досягнутий крок, параметр sweep і діапазон значень (якщо є), загальний час обробки, середній ms/word, середній час валідації, задіяні вчителі/студенти/стратегії промпту/архетипи/bias, конфігурація RAG якщо увімкнено.
* **Порівняння Self-critic проти оцінювання вчителем** — вибір двох запусків, що обчислює різницю (delta) частки успішних відповідей між будь-якими двома запусками, найкорисніше — коли один запуск оцінено в режимі self-critic, а інший — моделлю-вчителем над порівнянним вмістом. Це явно діагностичний сигнал, а не перевірка правильності: частка успішних відповідей жодного із запусків не є еталоном істини, оскільки і суддя self-critic, і суддя-вчитель мають власні упередження. Велика різниця вказує на те, що модель завищує власну самооцінку відносно зовнішнього судді; мала різниця означає, що обидва оцінювання загалом узгоджені для цієї моделі. Лише періодичний перегляд людиною вибірки оцінених відповідей може встановити, яке оцінювання дійсно ближче до правильного — це порівняння звужує, де шукати, а не замінює цей перегляд.

### Analytics (`/analytics`)

Три під-вкладки графіків, побудованих безпосередньо з персистованих відповідей одного запуску.

* **Adherence & metrics** — теплокарта дотримання (student x значення sweep, середня частка успішних); розподіл навантаження; розподіл затримки; швидкість генерації (ms/word); реальна швидкість генерації в токенах за секунду (з власного звітування часу Ollama, а не похідна оцінка); стабільність кількості слів; лексична різноманітність; відстань Левенштейна до тексту промпту/bias; семантичне перекриття; діаграма розсіювання психолінгвістичної сигнатури; частка успішних відповідей та стабільність зв'язності за стратегією промпту.
* **High-Dim analytics** — два графіки паралельних категорій (student/teacher/archetype/pass-fail, розфарбовані двома різними способами); матриця продуктивності моделі (ms/word за student, з фасетами за teacher); матриця розсіювання впливу вчителя та матриця міжмодельної залежності, обидві за лексичною щільністю, ms/word та когнітивним навантаженням.
* **Zipf deviation** — графіки розподілу та за архетипом відхилення кожної відповіді від розподілу частоти слів, характерного для природної мови (закон Ципфа); нижчі значення вказують на вихід, ближчий до типової статистики природної мови.

### NLP Science (`/nlp`)

Три під-вкладки, кожна — окрема панель лінгвістичних ознак, обчислена через ті самі модулі обчислення метрик, що вже використовують каскад та сторінки аналітики.

* **NLP-1** — профіль морфології частин мови (розподіл прикметників/іменників/дієслів); когнітивна складність (індекс читабельності проти лексичної різноманітності); емоційна залученість (суб'єктивність проти тональності).
* **NLP-2** — емоційна стабільність (варіативність тональності між реченнями); патерни повторюваності/фіксації.
* **NLP-3** — розподіл довжини речень; самофокусування проти когнітивної ригідності, у двох варіантах (загалом та з розбивкою за bias); розподіл ригідності за типом bias; абстракція проти когнітивного навантаження; розподіл наративної зв'язності; емоційна волатильність (варіативність тональності між сусідніми реченнями).

Уточнення формул відносно оригінального документа:

* **Когнітивне навантаження** — нормалізована композитна величина з трьох показників: довжина речення, щільність пунктуації та частка підрядних сполучників — кожен нормалізований мін-макс методом до діапазону [0, 1] перед усередненням. Формула оригінального документа (складні слова поділені на загальну кількість слів) описувала більш ранню, ненормалізовану версію, де сира величина довжини речення домінувала в середньому, а два інші компоненти майже не впливали на результат. Поточна формула:

$$
Cognitive\ Load = \frac{\overline{Довжина\ речення} + \overline{Щільність\ пунктуації} + Частка\ сполучників}{3}
$$

де кожен із перших двох доданків обмежений і нормалізований до [0, 1] перед усередненням, а частка сполучників природно обмежена діапазоном [0, 1].

* **Індекс самофокусування:**

$$
SelfFocus = \frac{Self\ Pronouns}{Total\ Pronouns}
$$

* **Показник повторюваності:**

$$
Repetition = \frac{Repeated\ Tokens}{Total\ Tokens}
$$

* **Ригідність речень:**

$$
Rigidity = \frac{Imperatives + Repetitions}{Total\ Sentences}
$$

### Clustering (`/clusters`)

Три під-вкладки над повним набором метрик одного запуску.

* **K-Means (PCA)** — діаграма розсіювання в проєкції PCA, розфарбована за обраним виміром, головні фактори-драйвери за кожною віссю та таблиця чистоти кластерів.
* **HDBSCAN (Density)** — діаграма розсіювання кластеризації на основі щільності над повновимірним масштабованим набором ознак, з автоматичним визначенням шуму/аутлайєрів.
* **Behavioral topology** — найповніший вигляд кластеризації: проєкція зменшення розмірності UMAP з подальшою кластеризацією HDBSCAN, графік мінімального кістякового дерева та графік згорнутого дерева (обидва можуть бути недоступні на дуже малому наборі даних), матриця кореляції ознак та діаграми розсіювання по парах ознак у дослідницькому режимі, розбивка аутлайєрів за моделлю, та підтверджувальні індекси якості кластеризації нижче.

Індекси якості кластеризації (без змін відносно оригінального документа — це стандартні формули, на які переписування не вплинуло):

* **Silhouette score:**

$$
s(i) = \frac{b(i) - a(i)}{\max\{a(i), b(i)\}}
$$

де $a(i)$ — середня відстань до точок того самого кластера, а $b(i)$ — середня відстань до найближчого іншого кластера.

* **Davies–Bouldin index:**

$$
DBI = \frac{1}{k} \sum_{i=1}^{k} \max_{j \neq i} \frac{\sigma_i + \sigma_j}{d(c_i, c_j)}
$$

* **Adjusted Rand Index (узгодженість міток з архетипами):**

$$
ARI = \frac{RI - E[RI]}{\max(RI) - E[RI]}
$$

Ці три індекси є рівнем підтверджувальної валідації на рівні корпусу: це окрема стадія від каскаду на рівні одної відповіді вище, змістовна лише для накопиченого корпусу, ніколи — для однієї відповіді.

### Model Evaluation (`/model_evo`)

* **Вибір цільового стовпця** — будь-який дискретний стовпець у наборі метрик запуску з кількістю унікальних значень від 2 до 10 (евристичний фільтр, а не жорстке правило про те, які стовпці є змістовними цілями).
* **Test size** — частка розбиття train/test.
* **Навчання** — базовий класифікатор логістичної регресії, натренований на числових метриках запуску для прогнозування обраного цільового стовпця.
* **Результат** — accuracy, precision, recall, F1-score, теплокарта матриці помилок та графік важливості ознак.

$$
Accuracy = \frac{TP + TN}{TP + TN + FP + FN}
\qquad
Precision = \frac{TP}{TP + FP}
\qquad
Recall = \frac{TP}{TP + FN}
\qquad
F1 = 2 \cdot \frac{Precision \cdot Recall}{Precision + Recall}
$$

### Benchmark (`/benchmark`)

Кросмодельна таблиця лідерів над одним запуском, лише для читання.

* **Overview** — кількість прикладів, кількість валідних прикладів, задіяні студенти/вчителі.
* **Pass rate** — частка успішної валідації для кожної моделі.
* **Inference speed** — швидкість генерації для кожної моделі, менше значення краще.
* **Теплокарта метрик якості** — зв'язність, когнітивне навантаження, лексична щільність, семантичне перекриття, коефіцієнт розширення.
* **Таблиця лідерів та модель-переможець** — ранжування за композитним фінальним балом.

$$
FinalScore = 0.4 \cdot PassRate + 0.3 \cdot Coherence + 0.3 \cdot SpeedScore
$$

Ця формула відрізняється від ранішої версії цієї таблиці лідерів, яка також враховувала "показник наслідування" (mimicry score), похідний від семантичного перекриття з текстом bias/архетипу. Цей компонент було видалено: семантичне перекриття з текстом bias — це саме те, що Layer 1 каскаду оцінювання використовує для виявлення та відхилення відповідей-відлуння, тож винагорода за *вище* значення тієї самої величини, яку каскад штрафує, була реальним, прямим протиріччям між двома частинами одного застосунку, а не стилістичним рішенням. Порівнянної метрики-заміни ("близькість до еталонного виходу вчителя") наразі не існує в персистованих даних, тому вагу було перерозподілено, а не замінено неперевіреним замінником.

### System Monitor (`/monitor`)

Свідомо вузький за обсягом, за явним рішенням: інспектор схеми та даних лише для читання, а не панель керування сервісами.

* **Таблиця схеми/типів даних** — кожен стовпець, присутній у даних запуску, з визначеним типом даних та кількістю непорожніх значень.
* **Попередній перегляд сирих даних** — відповіді запуску у вигляді звичайної таблиці.

Керування моделями Ollama (завантаження, перегляд списку, видалення моделей) не є частиною цієї сторінки. Оригінальний документ описував інтерфейс завантаження моделей та кнопки видалення для кожної моделі; ця функціональність тут існує лише як окрема, свідомо винесена за межі обсягу задача, оскільки включає виконання підпроцесів та деструктивне видалення — інший профіль ризику порівняно з рештою цієї сторінки, призначеної лише для читання. Керування моделями виконується безпосередньо з термінала (`ollama pull`, `ollama list`, `ollama rm`) або через операційну консоль, описану нижче.

### Export to Database (`/db_export`)

Відсутня в оригінальному документі; ця сторінка не існувала, доки основний адаптер сховища не було під'єднано до діючої кінцевої точки.

Кожна відповідь за замовчуванням зберігається як файли JSONL. Існує другий, повністю протестований бекенд зберігання над реальними таблицями SQLite (`runs`, `responses`), корисний для довільних SQL-запитів над накопиченими результатами; це не основний шлях запису, лише копія за запитом.

* **Список запусків** — кожен відомий запуск, з ID, часом початку та загальною кількістю задач.
* **Send to DB** — копіює метадані одного запуску та кожну відповідь у базу даних SQLite. Повторне надсилання вже експортованого запуску за замовчуванням відхиляється з чітким повідомленням, а не мовчки дублює кожен рядок відповіді; окрема дія повторного експорту виконує явну перезапис (overwrite).
* **Групове вибирання** — прапорці плюс дія "надіслати обрані". Груповий експорт запускає власну індивідуальну дію експорту для кожного обраного рядка; кожен рядок усе одно вирішується незалежно, з такою самою поведінкою вже-експортовано/перезапис, яку дав би одиночний клік.
* **Стовпець статусу експорту** — повідомляє або "не синхронізовано", або точну дату й час останнього копіювання запуску в базу даних, оновлюється наживо після завершення експорту, без перезавантаження сторінки.

Та сама операція доступна з термінала без запущеного сервера, через операційну консоль (`python -m cli.manage export-db <run_id>`), а також як прямий виклик API (`POST /db_export/export?run_id=...`).

### Операційна консоль

Відсутня в оригінальному документі, який не мав відповідника безголового (headless) адміністративного інтерфейсу. Точка входу командного рядка для операцій, що не потребують запущеного веб-інтерфейсу:

* `serve` — запускає веб-застосунок (еквівалент задокументованої команди `uvicorn`).
* `status` — повідомляє про доступність Ollama, NLTK та spaCy, ті самі перевірки, що виконує віджет статусу сервісів у бічній панелі, у формі, читабельній у терміналі.
* `list-runs` — перелічує кожен відомий запуск.
* `export-db <run_id>` — еквівалент сторінки Export to Database для командного рядка.

### FAQ (`/faq`)

Статична сторінка посібника користувача та методологічного довідника, доступна англійською та українською мовами.

* Чому теплокарта дотримання показує 0%? — Зазвичай через значення Temperature, встановлене занадто високим, або слабку модель-вчитель.
* Для чого потрібен Blind mode? — Перевірити, чи модель усе одно відтворює стиль цільового архетипу без прямої вказівки назви архетипу.
* Що перевіряє каскад оцінювання і в якому порядку? — Див. "Каскад оцінювання" вище; спочатку Layer 0, останнім — Layer 3 (генеративний суддя).
* У чому різниця між оцінюванням Self-critic та Teacher–student? — Self-critic використовує ту саму модель для генерації та оцінювання, задокументований ризик того, що модель віддає перевагу власному виходу; Teacher–student використовує окрему модель для оцінювання.
* Як слід використовувати різницю (delta) self-critic проти оцінювання вчителем? — Як діагностику того, наскільки модель надмірно довіряє власному судженню відносно зовнішньої моделі, а не як визначення, яке судження правильне.
* Чому показник наслідування (mimicry score) було видалено з таблиці лідерів? — Він винагороджував саме ту поведінку, яку Layer 1 каскаду оцінювання створено відхиляти; див. "Benchmark" вище.
* Для чого потрібен режим RAG? — Retrieval-augmented generation: додавання у промпт генерації контексту з бази знань, релевантного архетипу та/або bias.
* Чи можна використовувати результати поза аналізом психолінгвістичного стилю? — Так; ті самі метрики застосовні до будь-якого завдання порівняння стилю, жанру, формальності чи мовної різноманітності, не лише до випадку обумовлення архетипом, для якого цей застосунок був створений.
* Де фактично зберігаються дані? — За замовчуванням у файлах JSONL; SQLite — лише якщо явно експортовано через сторінку Export to Database чи команду консолі.
